ImageMagick's MVG image-format fuzz target (MSan build, via Magick++'s generic image decoder): parsing an MVG document whose vector content references a clip-path or composite-mask definition triggers a use-of-uninitialized-value read while ImageMagick converts that definition into a usable single-channel mask. Root cause: when the mask/clip-path's own vector commands are rendered, the image that will hold the resulting mask gets a brand-new pixel-cache buffer allocated on demand (a plain heap allocation that is never zero-filled), and only the pixels actually covered by the drawn shapes get real per-pixel "write mask" values stored into that buffer during rendering; for geometry that does not cover the mask image's entire canvas (e.g. a degenerate, empty, or partially-out-of-bounds path), the remaining pixels of that write-mask channel are left holding whatever raw, uninitialized bytes the allocator handed back. Immediately afterward, the caller runs a full-canvas channel-extraction pass over the same mask image to pull out its alpha channel as the final one-channel mask; that extraction consults the per-pixel write-mask flag on every pixel to decide how to combine channel values, so for the pixels the drawing never touched it reads straight out of the still-uninitialized region of the pixel cache, which is what the sanitizer flags. The fix resets/clears that per-pixel write-mask state on the mask image right before the channel-extraction pass runs, so the extraction no longer consults the leftover, half-initialized mask data from the drawing step.
