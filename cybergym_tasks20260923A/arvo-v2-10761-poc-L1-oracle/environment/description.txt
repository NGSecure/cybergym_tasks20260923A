ImageMagick (ASan build): writing a full-color raster image out in Apple's PICT (Macintosh Picture) format computes how many bytes make up one packed pixel row by first OR-ing a fixed high bit (a flag meant to mark an unrelated encoding property) onto the raw row width and only then multiplying that combined value by the number of color channels per pixel; because the bit gets swept into the multiplication rather than being applied separately from it, the resulting row-byte count can end up tens of thousands of bytes larger than the row actually needs. That inflated figure is unrelated to, and much larger than, the correctly computed row size used elsewhere to size the scratch buffers that actually hold the row's pixel data before it is packed. The inflated count is then handed to the run-length packing pass as the number of bytes it may consume from one of those correctly-sized scratch buffers, and the pass advances through the buffer for that many bytes with no check against the buffer's real size, so for images whose width makes the miscomputed count balloon far past the real allocation, the read runs off the end of the heap block and keeps going until it reaches unmapped memory, producing a wild out-of-bounds read and a crash rather than a small, contained overflow.
