ImageMagick's PNG/MNG writer (reached while encoding a multi-image MNG stream) feeds a partially-populated scanline buffer into libpng's compressor, and MemorySanitizer catches the gap only two layers further down, inside zlib's own sliding-window bookkeeping during row compression, when the uninitialized bytes are copied into the compressor's internal window. Root cause: before building the output color palette/bit-depth decision, the encoder directly overwrites the image's depth field with the value returned by a pure inspection helper that scans pixel values and reports the minimal bit depth needed to represent them losslessly but never touches the pixel storage itself. This is different from the sibling routine that actually rewrites every pixel sample to fit a given bit depth. Because the assignment updates only the depth metadata and not the underlying quantum pixel data, the encoder's later per-row export/pack/color-type selection logic can end up operating on a depth value that no longer matches how the pixel data is actually laid out; the heap-allocated per-row pixel buffer it hands off to libpng's write-row/pack/transform path is then not fully written before that data is copied onward, so trailing bytes stay uninitialized all the way through to the compressor's window-fill step. The fix replaces the blind reassignment with a check that only invokes the real, fully-initializing bit-depth conversion when the freshly computed depth actually differs from the image's current depth, keeping the depth metadata and the real pixel representation in sync.
