This is an out-of-bounds read in HarfBuzz's AAT "kerx" state-machine kerning path (format-1 subtable) that MemorySanitizer flags as an uninitialized/unmapped 16-bit read while a pending kern value is being popped off an internal stack and applied to a buffered glyph. When an action entry in the state table requests a kern application, the code needs to read a short run of 16-bit kerning values from the subtable's action array, one value per stack entry, but the values for a given stack slot are not contiguous -- font data specifies how many 16-bit "tuple" slots separate one stack entry's value from the next, and that stride is taken straight from an attacker-controlled header field with no upper limit imposed on it. Before consuming the array, the code is supposed to bounds-check the full span it is about to touch by multiplying the (small, stack-bounded) number of entries to pop by that attacker-controlled stride and validating the resulting extent against the sanitized table region. That multiplication is done as an ordinary fixed-width unsigned integer without first checking whether the two operands overflow it: a small pop count combined with a stride close to the field's maximum value wraps the product down to a tiny number, so the bounds check happily validates only a few bytes near the start of the array. The subsequent loop, however, still advances the read cursor by the real, un-wrapped stride on every iteration, so after the first couple of pops it has walked far past the validated (and past the whole sanitized) region and dereferences a wild pointer to decode the next big-endian kerning value, producing the reported read crash. Note that this project has other independently-tracked kerx/morx state-table bugs; the defining fingerprint here is specifically the stride-multiplication overflow that lets an undersized bounds check pass before an unbounded per-entry stride walks the cursor out of range.
